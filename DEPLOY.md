# Deploying pulse

Target: a public URL a stranger can open, with **no recurring cost**.

## Shape of the deployment

```
Neon (free Postgres)  <—  Render web service (free)
                             ├── Express API
                             ├── the built dashboard (same origin)
                             └── ingestion + spike detection, in-process
GitHub Actions (free) ——> pings /health every 10 min to prevent spin-down
```

**One service, not two.** Render's free tier covers web services but not
background workers, so a $0 deployment runs ingestion and detection inside the
web process (`RUN_WORKER_IN_API=true`). Locally the standalone worker is still
the better choice — it restarts independently of the API — but paying for a
second service to get that in production is not worth it here.

**Same origin for API and dashboard.** No CORS to configure, no cross-site
cookie rules, and the SSE stream is same-origin by construction.

## 1. Database (Neon)

1. Create a project at [neon.tech](https://neon.tech) — free tier, no card.
2. Copy the connection string.

> **Check `/health` rather than assuming.** Live updates use `LISTEN/NOTIFY`,
> which a transaction-mode connection pooler can break: it accepts `LISTEN`
> without error and then never delivers, because the `NOTIFY` lands on a
> different backend.
>
> pulse does not guess. At startup it sends itself a probe notification and
> falls back to 2s polling if it does not come back, so `/health` reports what
> is actually working — `streamSource: "notify"` or `"poll"`.
>
> **Measured on this deployment (2026-09-05):** a Neon connection reported
> `notify` with the probe active, so notifications round-trip there. An earlier
> revision of this file claimed Neon's pooled endpoint could not support
> `LISTEN/NOTIFY`; that was asserted rather than tested, and the probe
> contradicts it. If you see `poll`, switch to the direct (non-`-pooler`)
> connection string.

## 2. Web service (Render)

`render.yaml` is a Blueprint: point Render at the repository and it reads the
build command, start command, health check, and non-secret environment.

Set these in the Render dashboard (they are marked `sync: false` so they never
touch the repository):

| Variable | Value |
|---|---|
| `DATABASE_URL` | the Neon direct connection string |
| `GEMINI_API_KEY` | from [aistudio.google.com/apikey](https://aistudio.google.com/apikey) |
| `ADMIN_USER_EMAIL` | your email |
| `ADMIN_USER_PASSWORD` | 12+ characters, generated not chosen |
| `DEMO_USER_PASSWORD` | fine to be public; the account is read-only |

`JWT_SECRET` is generated by Render once and kept. **The app refuses to boot in
production without one** — a predictable signing key is a complete auth bypass.

Generate the admin password with:

```bash
node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
```

> **Keep billing OFF on the Google Cloud project behind `GEMINI_API_KEY`.**
> Enabling it removes the free tier for that project entirely and every call
> becomes billable from the first token.

## 3. Accounts

Migrations **and seeding** both run during build, so the demo and admin accounts
exist as soon as the first deploy finishes. Seeding is idempotent (it upserts),
so it is safe on every deploy, and it reads the passwords from the environment
rather than the repository.

If `ADMIN_USER_PASSWORD` is unset the build still succeeds and simply skips the
admin account, logging that it did — the demo account is what the public link
needs.

## 4. Keep it awake (optional but recommended)

Render's free tier spins a service down after ~15 minutes without traffic, and a
spun-down service ingests nothing and takes ~50s to answer the first request.

Set a repository variable `PULSE_URL` to your Render URL and the bundled
`.github/workflows/keepalive.yml` pings `/health` every 10 minutes. Without it
the demo still works — the first visitor just waits for the cold start, and
ingestion only runs while someone is looking.

## Verifying the deployment

### The acceptance criterion

Open the URL in a private window. The dashboard should load with **no login**
and show live data. That is the whole test.

### The abuse audit

The requirement is that no public or demo-role endpoint can trigger Gemini,
Twilio, or an on-demand scrape. This is enforced by tests, not a checklist —
checklists get read once and then rot:

```bash
npx vitest run apps/api/src/abuse-audit.test.ts
```

It proves three things:

1. **Coverage.** Every route the Express router exposes is classified. Adding a
   route without classifying it fails the audit.
2. **Behaviour.** With `global.fetch` stubbed, every anonymous and demo-role
   route is called and **zero outbound requests** are made. Gemini, Twilio and
   every ingestion source all go over `fetch`, so one assertion covers all three
   hazards. This runs against a *fully configured* instance — real-looking
   credentials present — so it proves the guards hold, not merely that an
   unconfigured box cannot spend.
3. **Structure.** The module graph reachable from the anonymous route files
   never reaches `@pulse/scoring` or `@pulse/alerting`. A future edit that wires
   one in fails immediately rather than at the first surprise invoice.

Plus: the scoring trigger is admin-only (401 anonymous, 403 demo) and capped at
60 posts per call, so even a stolen admin token cannot drain the day's quota in
one request.

### Manual spot check

```bash
curl -s https://YOUR-URL/health
curl -s -o /dev/null -w '%{http_code}\n' https://YOUR-URL/api/admin/watchlist   # expect 401
```

`/health` reports:

- `commit` — which build is actually serving. Render's free tier spins down, so
  a reset uptime means either a redeploy or a wake-up; without this you cannot
  tell, and every check against the live URL is a check against an unknown
  build.
- `streamSource` — `notify` or `poll`, established by an actual delivery probe
  rather than by assuming a successful `LISTEN` means anything.
- `workerInProcess` — whether ingestion is running inside the web service.

## Known limitations, stated rather than hidden

- **Spin-down.** On the free tier, ingestion only runs while the service is
  awake. The keepalive workflow mitigates it; it does not eliminate it.
- **The rate limiter is in-process.** It resets on restart, and two instances
  would each allow the full budget. Correct for one small instance; a horizontal
  scale-out needs a shared store.
- **`TRUST_PROXY=1` is required** behind Render. Without it every request looks
  like it came from the proxy and the first client to hit 60 requests/minute
  locks out everyone.
- **Ingestion shares a process with the API.** A crash in the ingestion loop is
  caught and logged so the dashboard stays up, but heavy ingestion competes with
  request handling on one free-tier CPU.
- **A transaction-mode pooler can degrade live updates to polling.** The
  startup probe detects it and `/health` reports the truth; it is not silent
  either way.
